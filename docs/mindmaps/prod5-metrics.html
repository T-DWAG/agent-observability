Production Topic 05

Metrics 预聚合

后台重算、持久化物化快照。把 HTTP 请求里的 N+1 扫描移出读路径，让查询稳定为一次 tenant + scope 读取。

01主链路

Ticker / Cold Start
→
Aggregator.calculate
→
Trace + Span 扫描
→
Upsert Snapshot
→
GET O(1)

02改造前后

现在：请求时聚合

cache miss 后分页读 Trace，并逐条查 Span。进程重启缓存清空，多实例不共享。

专题 5：持久化快照

后台承担重计算。API 按 tenant + scope 读取一行，重启后快照仍然存在。

03为什么不直接增量 +1

  • SaveTrace 有重试与 upsert，不是 exactly-once 事件。
  • 采样淘汰、TTL 删除后需要反向扣减。
  • 工具计数依赖 Span 完成时机。
  • 无幂等账本时，增量桶会快但不准。

04唯一键

tenant_id
租户隔离
scope
24h / 7d / 30d
UNIQUE
同组合覆盖写

05职责

  • Calculator：从真实数据算对
  • Storage：快照 upsert / get
  • Refresher：周期重算
  • API：读取；冷启动兜底

06新鲜度

  • 默认刷新：1m
  • 返回 refreshed_at
  • 失败保留旧快照
  • 最终一致，不伪装实时

07正确性闭环

采样 / TTL
→
原始 Trace 改变
→
下一轮全量重算纠正
刷新前不删除旧快照。某次计算失败只记录日志，查询继续使用最后一次成功结果。

08验收

  • 相同 tenant + scope 刷新两次仍只有一行。
  • A/B 租户快照互不影响。
  • Refresh 后新增 Trace，GET 仍读旧快照；再次 Refresh 才更新。
  • Purge 后刷新能纠正总数。
  • PostgreSQL 重启后快照仍可读取。

09边界

本章不做分钟/小时桶、幂等消费账本、ClickHouse、Redis、Eval 趋势和分布式锁。等后台全量重算真的成为瓶颈，再升级到“时间桶 + 定期校准”。
